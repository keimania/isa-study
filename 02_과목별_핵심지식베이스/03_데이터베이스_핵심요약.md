# 제3과목: 데이터베이스 종합 마스터 가이드

본 가이드는 정보시스템감리사 제3과목(데이터베이스)의 전 출제 범위를 집대성한 심화 이론서로, 데이터 모델링 및 정규화/반정규화 이론, 관계대수, 고급 SQL(윈도우/계층형), 트랜잭션 ACID, 동시성 제어(2PL/MVCC), 장애 회복(ARIES), 쿼리 옵티마이저 및 3대 조인 알고리즘, NoSQL/분산 데이터 아키텍처를 총망라합니다.

---

## 1. 데이터 모델링 및 ANSI-SPARC 3단계 구조

### (1) 데이터베이스 3단계 스키마 구조 및 독립성
*   **외부 스키마 (External Schema / 사용자 뷰)**: 개별 사용자나 응용프로그램 관점에서 바라본 데이터베이스 구조 (여러 개 존재).
*   **개념 스키마 (Conceptual Schema / 논리적 뷰)**: 전체 데이터베이스의 논리적 구조, 엔티티, 관계, 제약조건을 기술 (조직 전체에 단 하나만 존재).
*   **내부 스키마 (Internal Schema / 물리적 뷰)**: 실제 물리적 저장장치 상의 레코드 레이아웃, 인덱스, 블록 구조, 내부 데이터 표현.

> **2대 데이터 독립성 (Data Independence)**:
> 1.  **논리적 데이터 독립성**: 개념 스키마가 변경(컬럼 추가 등)되더라도 **외부 스키마(응용프로그램)는 영향을 받지 않는 성질** (외부/개념 사상 변경으로 흡수).
> 2.  **물리적 데이터 독립성**: 내부 스키마(인덱스 재구성, 저장장치 변경 등)가 변경되더라도 **개념 스키마와 외부 스키마는 영향을 받지 않는 성질** (개념/내부 사상 변경으로 흡수).

### (2) 식별자 (Identifier) 분류 및 관계 설계

| 분류 기준 | 식별자 유형 | 특징 및 설계 기준 |
| :--- | :--- | :--- |
| **대표성 여부** | **주 식별자 (Primary)** | 엔티티 내의 각 인스턴스를 유일하게 식별하며, NULL을 허용하지 않고(Not Null), 자주 변하지 않음 |
| | **보조 식별자 (Alternate)** | 인스턴스를 식별할 수 있으나 주 식별자로 선택되지 못한 후보키 (대체키, 유니크 인덱스 생성) |
| **스스로 생성 여부**| **내부 식별자 (Internal)** | 다른 엔티티의 참조 없이 자신의 엔티티 내부에서 스스로 생성되는 식별자 |
| | **외부 식별자 (Foreign)** | 타 엔티티와의 관계(Relationship)를 통해 상속받아 참조하는 식별자 (외래키 역할) |
| **단일 속성 여부** | **단일 식별자 (Single)** | 단 하나의 속성으로만 구성된 식별자 (예: 사원번호) |
| | **복합 식별자 (Composite)** | 둘 이상의 속성이 결합되어야 인스턴스를 고유하게 식별하는 식별자 (예: 학번 + 과목코드) |
| **대체 여부** | **본질 식별자 (Natural)** | 실제 업무적으로 의미가 있는 본래의 고유 속성 (예: 주민번호, 사업자번호, 이메일) |
| | **인조 식별자 (Surrogate)** | 복합 식별자가 너무 길거나 본질 식별자의 보안/변경 위험으로 인해 임의 부여한 일련번호 (예: 주문ID, 시퀀스) |

#### 식별 관계 (Identifying) vs 비식별 관계 (Non-Identifying)
*   **식별 관계 (실선 표기)**:
    *   부모 엔티티의 주 식별자를 자식 엔티티의 **주 식별자(PK)의 일부**로 상속받음.
    *   부모가 없으면 자식 인스턴스가 존재할 수 없는 강한 종속성(강한 개체).
    *   *단점*: 자식 엔티티가 하위로 계속 확장될수록 주 식별자 속성 수가 과도하게 늘어나 복합키 인덱스 부담 증가.
*   **비식별 관계 (점선 표기)**:
    *   부모의 주 식별자를 자식 엔티티의 **일반 속성(FK)**으로만 상속받음.
    *   부모와 자식의 생명주기가 독립적(약한 종속성)이거나 상위 식별자가 부모 없이 생성 가능한 경우.

## 2. 정규화 이론 (Normalization) 및 반정규화

### (1) 정규화 단계별 함수 종속 제거

```mermaid
flowchart LR
    A["비정규 릴레이션"] -->|"도메인 원자값"| 1NF["1NF"]
    1NF -->|"부분함수종속 제거"| 2NF["2NF"]
    2NF -->|"이행함수종속 제거"| 3NF["3NF"]
    3NF -->|"모든 결정자가 후보키"| BCNF["BCNF"]
    BCNF -->|"다치종속 제거"| 4NF["4NF"]
    4NF -->|"조인종속 제거"| 5NF["5NF"]
```

1.  **제1정규형 (1NF)**:
    *   릴레이션의 모든 도메인이 **원자값(Atomic Value)**만으로 구성되어야 함.
    *   반복 그룹(Repeating Group) 또는 1개 컬럼에 다중 값(예: 전화번호 2개 이상)이 들어가 있으면 분리.
2.  **제2정규형 (2NF)**:
    *   1NF를 만족하고, 기본키의 진부분집합이 일반 속성을 결정하는 **부분 함수 종속성(Partial Functional Dependency)을 제거**하여 **완전 함수 종속(Full FD)**을 달성.
    *   *(주의)*: 기본키가 단일 속성인 경우 이미 부분 함수 종속이 발생할 수 없으므로 1NF 만족 시 자동으로 2NF를 만족함.
3.  **제3정규형 (3NF)**:
    *   2NF를 만족하고, 기본키가 아닌 일반 속성 간에 종속 관계가 성립하는 **이행적 함수 종속성($X \rightarrow Y, Y \rightarrow Z \implies X \rightarrow Z$)을 제거**.
4.  **보이스-코드 정규형 (BCNF: Boyce-Codd Normal Form)**:
    *   3NF를 만족하고, 릴레이션에 존재하는 **모든 결정자(Determinant)가 반드시 후보키(Candidate Key)여야 함**.
    *   후보키가 여러 개이고 이들이 복합키이며 서로 중첩(Overlap)될 때 발생하는 이상현상 해결.
5.  **제4정규형 (4NF)**:
    *   BCNF를 만족하고, 한 키에 여러 독립적인 속성들이 다대다 매핑되는 **다치 종속성(MVD: Multi-Valued Dependency, $X \twoheadrightarrow Y$)을 제거**.
6.  **제5정규형 (5NF, PJ/NF)**:
    *   4NF를 만족하고, 원래 릴레이션으로 복원할 때 조인 연산에 의해 발생하는 **조인 종속성(JD: Join Dependency)을 제거** (모든 조인 종속이 후보키에 의해서만 성립).

### (2) 반정규화(역정규화) 기법과 트레이드오프
정규화는 무결성을 극대화하지만 테이블 분할로 인해 다중 조인(Join)에 따른 디스크 I/O가 증가합니다. 성능 향상을 위해 반정규화를 적용할 수 있습니다.

*   **테이블 반정규화**:
    *   *테이블 병합*: 1:1 관계 병합, 1:N 관계 병합(조인 성능 개선), 서브타입 통합(Single Table 전략).
    *   *테이블 분할*:
        *   **수직 분할**: 칼럼 단위 분할. 사용 빈도가 높은 컬럼과 LOB(CLOB/BLOB) 등 큰 컬럼을 분리하여 버퍼 캐시 히트율 개선.
        *   **수평 분할(파티셔닝)**: 행 단위 분할. Range(날짜/범위), List(지역/코드), Hash(분산), Composite 파티셔닝.
*   **컬럼 반정규화**:
    *   중복 컬럼 추가(조인 회피용), 파생/집계 컬럼 추가(통계값 미리 계산 저장), 이력 테이블 기능 컬럼 추가.
*   **반정규화의 부작용**: 데이터 중복에 따른 **저장 공간 낭비**, 데이터 갱신 시 중복 레코드 전수 업데이트에 따른 **DML 성능 저하**, 일관성 불일치(데이터 무결성 훼손) 위험.

## 3. 관계대수 (Relational Algebra)

관계대수는 릴레이션을 다루는 절차적(Procedural) 언어입니다.

| 연산자 | 기호 | 연산 정의 | 차수(Degree) 및 카디널리티(Cardinality) |
| :--- | :---: | :--- | :--- |
| **Select** | $\sigma_{\text{조건}}(R)$ | 조건을 만족하는 **수평적 행(Tuple) 선택** | 차수: 변화 없음 ($= \text{deg}(R)$)<br>카디널리티: $\le |R|$ |
| **Project** | $\pi_{\text{속성}}(R)$ | 지정된 **수직적 열(Attribute) 선택** (중복 튜플 제거) | 차수: 지정된 속성 수<br>카디널리티: $\le |R|$ (중복 제거 시 감소) |
| **Join** | $R \bowtie_{\text{조건}} S$ | 두 릴레이션의 공통 속성 기준으로 조합 | 차수: $\text{deg}(R) + \text{deg}(S) - \text{공통속성수}$ (자연조인 기준) |
| **Division** | $R \div S$ | $S$의 모든 튜플 값을 포함하는 $R$의 튜플 반환 | 차수: $\text{deg}(R) - \text{deg}(S)$ |
| **Cartesian** | $R \times S$ | 두 릴레이션의 모든 튜플의 직적 조합 | 차수: $\text{deg}(R) + \text{deg}(S)$<br>카디널리티: $|R| \times |S|$ |

## 4. 트랜잭션, 동시성 제어 및 회복 기법

### (1) 트랜잭션의 4대 특성 (ACID) 및 구현 메커니즘
1.  **Atomicity (원자성)**: "All or Nothing". 트랜잭션의 연산은 전원 실행되거나 전원 취소되어야 함. $\rightarrow$ **Undo 로그**로 구현.
2.  **Consistency (일관성)**: 트랜잭션 완료 후 데이터베이스는 무결성 제약조건을 만족해야 함.
3.  **Isolation (격리성)**: 동시에 실행되는 트랜잭션들은 상호 간섭할 수 없음. $\rightarrow$ **Locking 및 MVCC**로 구현.
4.  **Durability (영속성)**: 성공적으로 커밋된 트랜잭션의 결과는 영구 보존됨. $\rightarrow$ **Redo 로그 및 WAL**로 구현.

### (2) 병행 제어 미수행 시 발생하는 4대 이상현상
1.  **갱신 분실 (Lost Update)**: 두 트랜잭션이 동일 데이터를 동시 갱신할 때 한 트랜잭션의 갱신 내용이 다른 갱신에 의해 덮어써져 사라지는 현상.
2.  **모순성 (Inconsistency / Non-Repeatable Read)**: 한 트랜잭션이 동일 데이터를 두 번 읽는 사이에 다른 트랜잭션이 해당 데이터를 갱신하여 두 번의 읽기 결과가 불일치하는 현상.
3.  **연쇄 복귀 (Cascading Rollback)**: 여러 트랜잭션이 연속으로 데이터를 조작하다가 한 트랜잭션이 실패하여 롤백될 때 이미 커밋되지 않은 데이터를 참조한 타 트랜잭션들까지 연쇄적으로 취소되어야 하는 문제.
4.  **미완료 의존성 (Dirty Read)**: 트랜잭션 A가 작업 중(아직 Commit 전)인 데이터를 트랜잭션 B가 읽었으나, 이후 A가 Rollback되어 B가 가짜 데이터를 읽게 된 현상.

### (3) SQL-92 격리 수준 (Isolation Levels) 정밀 비교

| 격리 수준 | Dirty Read 방지 | Non-Repeatable Read 방지 | Phantom Read 방지 | 특징 및 락(Lock) 메커니즘 |
| :--- | :---: | :---: | :---: | :--- |
| **Read Uncommitted** | ❌ 발생 | ❌ 발생 | ❌ 발생 | Commit되지 않은 데이터도 읽기 허용 (Shared Lock 없이 조회) |
| **Read Committed** | **⭕ 방지** | ❌ 발생 | ❌ 발생 | Commit된 데이터만 읽기 허용 (오라클, PostgreSQL 기본값, 읽기 완료 즉시 Shared Lock 해제) |
| **Repeatable Read** | **⭕ 방지** | **⭕ 방지** | ❌ 발생 | 트랜잭션 종료 시까지 읽은 데이터의 Shared Lock 유지 (MySQL InnoDB 기본값, MVCC로 팬텀리드까지 대부분 방지) |
| **Serializable** | **⭕ 방지** | **⭕ 방지** | **⭕ 방지** | 범위 락(Range Lock)을 적용하여 완벽한 직렬화 보장 (동시성 처리량 극히 저하) |

### (4) 2단계 로킹 규약 (2PL: Two-Phase Locking Protocol)
*   **확장 단계 (Growing Phase)**: 트랜잭션은 Lock만 획득할 수 있고 Unlock은 할 수 없음.
*   **축소 단계 (Shrinking Phase)**: 트랜잭션은 Unlock만 할 수 있고 새로운 Lock을 획득할 수 없음.
*   **특징**:
    *   **직렬 가능성(Serializability)을 100% 보장**.
    *   **교착상태(Deadlock)는 예방하지 못함** (상대방 자원의 Lock을 대기하며 Deadlock 발생 가능).
*   *Strict 2PL*: 모든 배타적 락(X-Lock)을 트랜잭션이 Commit 또는 Rollback될 때까지 유지 (연쇄 복귀 방지).
*   *Rigorous 2PL*: 공유 락(S-Lock)과 배타적 락(X-Lock) 모두를 트랜잭션 종료 시까지 유지.

### (5) MVCC (Multi-Version Concurrency Control)
*   데이터를 수정할 때 기존 데이터를 덮어쓰지 않고, **Undo 세그먼트에 이전 버전의 스냅샷 데이터를 보관**하고 SCN(System Commit Number) 타임스탬프를 부여.
*   조회 쿼리가 시작된 시점 이전의 SCN 데이터를 Undo 영역에서 읽어 일관된 읽기(Consistent Read) 수행.
*   **"읽기 작업은 쓰기 작업을 블록하지 않고, 쓰기 작업은 읽기 작업을 블록하지 않는다"**는 원리로 동시성 처리 성능 극대화.

| **Nested Loop (NL) Join** | 외부(드라이빙) 테이블의 각 행을 하나씩 추출하여 내부(드리븐) 테이블의 인덱스를 반복 탐색 (2중 For문) | • OLTP 환경의 소량 데이터 조인<br>• 드라이빙 테이블 조건 결과 행 수가 적고, 드리븐 테이블 조인 컬럼에 인덱스가 완벽히 존재할 때 | • 드리븐 테이블 조인 컬럼에 인덱스가 없으면 매 행마다 Full Table Scan 발생<br>• 대용량 데이터 시 랜덤 액세스 I/O 폭증 |
| **Sort Merge Join** | 양쪽 테이블을 조인 키 컬럼 기준으로 **각각 먼저 정렬(Sort)한 후 머지(Merge)** | • 조인 컬럼에 인덱스가 없을 때<br>• 비동등 조인(BETWEEN, <, >) 처리 시 | • 대용량 테이블 정렬 시 PGA 메모리가 부족하여 디스크 Temp Tablespace 사용 시 I/O 부하 심각 |
| **Hash Join** | 작은 쪽 테이블(Build Input)을 메모리에 올려 **해시 테이블을 구축**한 후, 큰 테이블(Probe Input)을 스캔하며 해시 함수로 매칭 | • **대용량 데이터의 DW/배치 조회**<br>• 조인 컬럼에 인덱스가 없는 대용량 동등(=) 조인 | • **오직 동등 조인(=)에서만 동작**<br>• Build Input이 해시 작업 메모리(Hash Area)를 초과하면 디스크 해시 분할(Grace Hash) 발생으로 성능 저하 |

## 6. NoSQL 및 빅데이터 분산 아키텍처

### (1) CAP 정리 vs PACELC 정리
*   **CAP 정리**: 일관성(Consistency), 가용성(Availability), 분할 허용성(Partition Tolerance) 중 2가지만 선택 가능. 네트워크 단절(P)은 분산 환경의 필연적 속성이므로 실질적으로 **CP vs AP**의 선택.
*   **PACELC 정리**:
    *   **P (네트워크 분할 시)**: **A (가용성)** vs **C (일관성)**
    *   **E (Else: 정상 상태 시)**: **L (지연 시간 Latency)** vs **C (일관성 Consistency)**
    *   예: MongoDB, HBase는 `PC/EC` (분할 시 일관성, 정상 시에도 일관성 중시), DynamoDB, Cassandra는 `PA/EL` (분할 시 가용성, 정상 시 짧은 지연시간 우선).

### (2) NoSQL 4대 데이터 모델 분류
1.  **Key-Value Store**: Redis, Memcached, Riak (가장 단순한 모델, 초고속 캐시).
2.  **Document Store**: MongoDB, CouchDB (JSON/BSON 형태, 비정형 데이터에 최적).
3.  **Column-Family Store**: Apache Cassandra, HBase (대용량 빅데이터 쓰기 최적화).
4.  **Graph Database**: Neo4j, Amazon Neptune (노드, 엣지, 속성으로 복잡한 네트워크 관계 탐색).
